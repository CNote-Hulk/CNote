LESSON: 8.1 – Metodologia de diagnostic

---

CONCEPT: Troubleshooting – definiție, principii și strategii

VERIFIED INFORMATION:
Troubleshooting = căutare logică, sistematică a sursei unei probleme pentru a restabili funcționarea. Necesită: identificare simptome → determinare cauză (prin eliminare) → confirmare soluție. Trei principii fundamentale: 1) reproducerea problemei, 2) simplificarea sistemului la minim, 3) cunoașterea funcționării normale. Două strategii complementare: simptomatică (case-based reasoning — bazată pe experiență, conexiuni simptom→cauză, rapidă, frecventă) și topografică (deep reasoning/first principles — cunoaștere profundă a sistemului, folosită la defecte noi). Corelația NU implică cauzalitate. Probleme intermitente: cele mai dificile (componente termic sensibile, metode statistice). Probleme multiple: substituția serială poate eșua.

CONCEPT: Root Cause Analysis (RCA)

VERIFIED INFORMATION:
RCA = metodă de identificare a cauzelor fundamentale ale defecțiunilor. Root cause = factorul a cărui eliminare PREVINE recurența (vs factor cauzal = doar contribuie). Cei 4 pași: 1) identificare/descriere problemă, 2) timeline normal→problemă, 3) distingere root cause vs factori cauzali, 4) graf cauzal. Management reactiv (simptome) vs proactiv (prevenire, RCA). Tehnici conform ISO/IEC 31010: Five Whys, FMEA, Fault Tree Analysis, Ishikawa diagrams, Pareto analysis. Exemplu: mașină oprită → siguranță → suprasarcină → lubrifiant → pompă → resturi metalice → cauza = lipsa filtrului. Acțiuni corective + effectiveness review.

CONCEPT: Metoda Half-splitting și divide-and-conquer

VERIFIED INFORMATION:
Half-splitting = aplicarea binary search pe lanțul de dependențe al unui sistem. Două strategii eficiente: 1) verificarea condițiilor frecvente/ușoare întâi, 2) bisecția sistemului. Similar jocului „20 de întrebări": 1 opțiune din 1.048.576 izolată în 20 pași (2²⁰). Foarte eficientă în sisteme cu lanțuri lungi de dependențe serializate. Sistemele cu feedback loops sunt mai puțin susceptibile la bisecție. Troubleshooting poate fi pre-organizat: checklists, proceduri, flowcharts, tabele.

CONCEPT: POST (Power-On Self-Test) ca instrument diagnostic

VERIFIED INFORMATION:
POST = proces firmware executat la pornire pentru detectarea componentelor nefuncționale. Verifică: registre CPU, integritate BIOS, DMA/timer/interrupt, memorie, dispozitive boot. Rezultate: ecran, LED-uri, beep codes (variază între producători). Beep codes: 1 scurt = OK, continuu = RAM absent, 1 lung + 2 scurte = display adapter. AMI: 1 = memory refresh, 2 = parity, 3 = memory R/W, 5 = processor, 8 = display memory. Evoluție: IBM original (test complet memorie, 5s–1,5 min) → modern (skip RAM test, boot rapid). Analogi console: LED patterns (RROD Xbox 360, YLOD PS3, BLOD PS4).

CONCEPT: FDIR aplicat hardware

VERIFIED INFORMATION:
FDIR (Fault Detection, Isolation and Recovery) = monitorizare → detectare defect → izolare → recovery. Detectare: discrepanța (rezidualul) între parametrii măsurați și valorile așteptate depășește pragul. Izolare: categorizare tip și localizare defecțiune. Recovery: oprire echipament defect, comutare la redundant, safe mode. Metode colectare date: vibrații, imaging termic, analiza particulelor. Strategii mentenanță: condition-based, planned preventive, corrective. Aplicare console: detectare (LED, imagine, sunet ventilator) → izolare sistematică (alimentare → APU → memorie → South Bridge → NAND) → recovery (reballing BGA, înlocuire componentă, reflow temporar).
